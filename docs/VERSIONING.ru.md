# Версионирование нашего SteamOS ARM для RP6

Этот документ задаёт правила собственных выпусков форка
`iddqdExe/SteamOS-ARM-Handhelds`. Рубеж полноценного выпуска описан в
[плане RP6](RP6-ROADMAP.ru.md#рубеж-полноценной-версии-rp6-100).
Автоматизацию этих правил реализуем в модуле 5; в текущей сборке она ещё
не подключена. Собственный выпуск пока не объявлен.

## Что получает версию

Версию получает весь комплект системы для RP6: образ microSD, ядро и
соответствующие модули/firmware, системные конфигурации, пользовательские
инструменты и пакет обновления, если он выпускается. Отдельная версия
InputPlumber, Mesa, Steam или upstream не является версией нашего проекта.

Схема основана на [SemVer 2.0.0](https://semver.org/lang/ru/).
Для этого проекта договорённость о совместимости охватывает документированные
способы установки и обновления, формат пакета и настроек, сохранение данных,
публичные команды/интерфейсы наших инструментов и заявленную поддержку RP6.

## Номера и стадии

Номер имеет вид `MAJOR.MINOR.PATCH`, например `1.2.3`.

| Изменение после 1.0.0 | Как увеличить номер | Пример |
| --- | --- | --- |
| Исправление ошибки, сохраняющее договорённость о совместимости | PATCH | `1.0.0` → `1.0.1` |
| Новая функция с совместимым обновлением и сохранением данных/настроек | MINOR, PATCH сбрасывается в 0 | `1.0.1` → `1.1.0` |
| Несовместимое изменение формата, интерфейса или способа установки/обновления; снятие заявленной поддержки | MAJOR, MINOR и PATCH сбрасываются в 0 | `1.1.0` → `2.0.0` |

Обновление upstream или ядра не определяет номер автоматически: номер выбирается
по результату для пользователя и совместимости. Поломка сохранения данных —
дефект, а не допустимый способ увеличить MAJOR. Плановое несовместимое изменение
должно иметь явную инструкцию перехода, сохранения данных и восстановления.

До 1.0.0 используем `0.x.y`: возможности и интерфейсы ещё формируются.
Завершение модуля не присваивает версию автоматически; версию назначаем
собранному и зафиксированному выпуску. Для первого тестового образа
планируется `0.1.0-alpha.1`, но этот номер пока не объявлен выпущенным.

| Стадия | Пример | Условие |
| --- | --- | --- |
| Alpha | `0.1.0-alpha.1` | Ограниченный набор реализованных функций; отсутствующие проверки перечислены |
| Beta | `0.4.0-beta.1` | Обязательные функции реализованы и базовые аппаратные проверки пройдены; общая приёмка ещё продолжается |
| Кандидат 1.0 | `1.0.0-rc.1` | Выполнен обязательный объём модулей 1–8; проверяем кандидат по рубежу 1.0.0 |
| Стабильный выпуск | `1.0.0` | Все условия рубежа подтверждены для итогового образа |

Числа в примерах показывают формат, а не обязательную нумерацию модулей.
Повторная тестовая сборка с изменённым содержимым получает следующий суффикс:
`alpha.1` → `alpha.2` или `rc.1` → `rc.2`. Для исправлений после 1.0.0
используем кандидаты следующей версии, например `1.0.1-rc.1`.

Опубликованный номер и Git-тег неизменяемы. Образ с новым содержимым нельзя
загрузить поверх старого под той же версией. Метаданные вида
`+g5ddfd5c` допустимы для локальных сборок, но не заменяют увеличение номера
опубликованного выпуска: SemVer не использует часть после `+` для сравнения
старшинства. Сборки из рабочей копии с незакоммиченными изменениями помечаются
`dirty` и не выпускаются как стабильные.

## Файлы и идентификаторы

В модуле 5 добавить следующую схему:

1. **`VERSION` в корне** — одна строка с номером проекта без префиксов,
   например `0.1.0-alpha.1` или `1.0.0`. Сборка и упаковка читают его;
   ручной ввод другого номера должен останавливать выпуск.
2. **`CHANGELOG.md`** — раздел `Unreleased` для текущих изменений, затем
   разделы выпущенных версий с датой, изменениями, совместимостью, миграциями,
   результатами RP6 и известными ограничениями.
3. **Git-тег** — `rp6-v<VERSION>`, например `rp6-v1.0.0`.
   Префикс отделяет наши теги от тегов upstream вроде `v1.3-beta9`.
   Тег указывает на точный коммит выпуска; его не перемещают.
4. **Образ** — `steamos-rp6-<VERSION>-sm8550.img` либо его сжатый вариант.
   Пакет обновления — `steamos-rp6-<VERSION>-sm8550-update.tar.gz`.
   На каждый распространяемый файл создаётся свой файл SHA256.
5. **Manifest выпуска** — версия проекта, полный Git SHA форка, ревизия/тег
   upstream, версия исходного Valve rootfs, версии и источники компонентов,
   конфигурация и инструменты сборки, контрольные суммы артефактов,
   проверенные модели и ссылки на протоколы аппаратной приёмки.
6. **Установленная система** — добавить `project_version`, `project_revision`
   и `upstream_revision` в существующий `/opt/steamos-sm8650/IMAGE.txt`.
   Показать версию в диагностике и существующей панели обновления.
   Поле `manifest.json.version` пакета обновления должно совпадать с `VERSION`.

Версию проекта нельзя записывать вместо версии Valve в `/etc/os-release`.
Сохраняем обе идентичности. Название существующего каталога `steamos-sm8650`
используется и сборкой SM8550; его переименование не требуется для начала
версионирования.

Сейчас `build-update-package.py` получает `--version` отдельно, а сборщик
образа ещё не записывает номер нашего проекта в `IMAGE.txt`. Модуль 5
должен связать эти пути с `VERSION` и проверять совпадение всех значений;
до этого номер в названии файла сам по себе не доказывает состав выпуска.

## Порядок выпуска

1. Выбрать следующий номер по изменениям и стадии готовности. Для 1.0.0
   проверить каждый пункт рубежа в плане; наличие исправлений в исходниках
   не заменяет приёмку образа.
2. Зафиксировать входы сборки и границы поддержки. При обновлении upstream
   записать его точную ревизию, проверить влияние на наши изменения и
   повторить соответствующие проверки RP6.
3. Обновить `VERSION` и раздел `CHANGELOG.md`. Зафиксировать изменения в Git;
   выпуск собирать из чистой рабочей копии этого коммита.
4. Собрать образ и, при выпуске обновления, пакет из того же набора компонентов.
   Проверить согласованность версии, ядра/модулей, карт управления и manifest.
5. Выполнить автоматические проверки и аппаратную приёмку для заявленной
   стадии. Для стабильного выпуска проверить установку, обновление с
   предыдущей совместимой версии и восстановление. Для первой 1.0.0
   исходной точкой обновления служит предыдущий наш тестовый выпуск.
   Испытания ведём на единственной microSD пользователя: до её перезаписи
   нужен полный проверенный backup на компьютере по [процедуре в плане](RP6-ROADMAP.ru.md#испытания-с-одной-microsd).
   Вторая карта не требуется; восстановление из backup учитывается отдельно
   от проверки целостности резервного файла.
6. Сохранить SHA256, manifest и протоколы испытаний. В описании указать,
   какие модели и сценарии проверены, какие ограничения остаются и как
   вернуться к предыдущей системе.
7. Создать аннотированный тег `rp6-v<VERSION>` на коммите выпуска и
   опубликовать собственный GitHub Release с этими артефактами.
   Alpha/beta/rc помечать как prerelease; `1.0.0` и последующие стабильные
   версии публиковать как обычные релизы только после их приёмки.

Не выбирать «последний тег» по всем тегам репозитория: сначала отделять
префикс `rp6-v`, затем сравнивать номера по SemVer. Стабильный канал получает
только стабильные выпуски; тестовый канал выбирается пользователем явно.
Автоматический выбор каналов и проверку версий в обновляторе реализуем
совместно с модулями 4–5, а не считаем уже доступными.

Если выпущенная версия имеет критический дефект, пометить её в описании как
не рекомендуемую, сохранить историю и выпустить исправление с новым номером.
Возврат к более старой версии проводится по проверенной процедуре модуля 4,
с учётом возможных несовместимых миграций; простое уменьшение `VERSION`
в исходниках откатом установленной системы не является.
